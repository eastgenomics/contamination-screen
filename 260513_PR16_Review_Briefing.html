03 Output schema rename

The most significant change is a rename of all output columns in summary.tsv and all related internal keys, CLI flags, and documentation. The original names overall_* and peak_* were ambiguous: it was unclear from the names alone which peak was the contamination signal and which was the germline-sharing peak. The new names make the distinction explicit.

The two peaks explained

The histogram of log2(VAF_B / VAF_A) always contains two regions of interest:

↑
The max peak
Formerly: overall_*

The tallest bin anywhere in the histogram, regardless of position. Usually the germline-sharing peak near log2=0 (ratio=1). Useful for detecting sample swaps, where two samples share identical variants at equal VAF.

New prefix: max_
≠
The non-unity peak
Formerly: peak_*

The tallest bin outside the unity zone (|log2| > 0.3). This is the contamination signal — variants from the source appearing at a consistent diluted fraction in the recipient. This peak drives all flagging decisions.

New prefix: non_unity_

The columns contamination_source, contamination_recipient, contamination_fraction, n_shared, n_shared_z, and flagged are unchanged.

Not a breaking change

The tool is not yet in production use, so this rename carries no downstream risk. It was applied cleanly throughout: output column names, internal dictionary keys, CLI flags, function parameter names, README column descriptions, and unit test assertion messages were all updated in a single commit (5971c48).

contamination_fraction precision — a documented limitation

The review also surfaced that contamination_fraction values cluster heavily around 0.5 for most flagged pairs. This is an inherent property of the bin-centre estimation approach: at --bin-width 0.2, the three bin centres near log2=−1 correspond to fractions 0.44, 0.50, and 0.57. The tool is designed for detection (is there contamination?) not precise quantification. The README column description now explicitly documents this as an estimate bounded by bin_width, not a measurement.

04 Bugs found and fixed

Bug 1 — Plot histogram bins misaligned with analysis bins

The most impactful bug. The histogram bars in PNG plot output did not match the non_unity_count value reported in summary.tsv. A run flagging a pair with non_unity_count=17 would show a tallest bar of 14 in the corresponding plot — a misleading discrepancy.

contamination_screen.py — write_plots() — bin edge calculation
Before
bins = np.arange(
  -_LOG2_RANGE,
  _LOG2_RANGE + bin_width,
  bin_width
)
After
bins = np.arange(
  -_LOG2_RANGE - bin_width / 2,
  _LOG2_RANGE + bin_width,
  bin_width
)

Root cause: _find_peaks() (which computes non_unity_count) uses bin edges offset by half a bin-width so that a ratio of exactly 1.0 falls at a bin centre rather than a bin edge. The plot in write_plots() used unshifted edges, producing a different binning of the same data. The fix applies the identical half-bin offset to the plot, so both use exactly the same bin boundaries and the bar heights match the reported counts.

Bug 2 — NameError crash in write_plots() when --plots is used

A secondary bug introduced during the variable rename (r → pair) in the same function. One reference was missed, meaning any run using --plots with at least one flagged pair would crash with a NameError: name 'r' is not defined at the title-setting step.

contamination_screen.py — write_plots() — plot title
Before
ax.set_title(
  f"{na[:45]} vs {nb[:45]}\n"
  f"n_shared = {r['n_shared']}",
  fontsize=8,
)
After
ax.set_title(
  f"{na[:45]} vs {nb[:45]}\n"
  f"n_shared = {pair['n_shared']}",
  fontsize=8,
)

Why it wasn’t caught earlier: the retrospective test run had been performed without matplotlib installed, so the --plots flag was silently skipped. The bug was caught by a second review pass specifically targeting the rename commit. Matplotlib has since been added to the test environment.

Lesson

When a rename touches a loop variable used across many lines of the same function, a targeted search (grep -n 'old_name') after the rename is faster and more reliable than relying on tests that may not exercise that branch.

05 Code quality and documentation

Several smaller issues were fixed alongside the bugs and the rename.

Loop variable name: r → pair

In write_plots(), the loop variable iterating over flagged pairs was named r — a single-letter name with no indication of what it represented. Renamed to pair throughout the loop body (which also exposed Bug 2 above when the missed reference became obvious).

Stale field names in test assertion messages

After the column rename, three assertion messages in tests/test_compare.py still referenced the old field names. The assertions themselves used the correct new keys (so tests passed), but if an assertion had fired, the error message would have raised a secondary KeyError trying to report the failing value — hiding the original failure behind a confusing second exception.

Control sample naming example

Both dx_fetch.py and README.md used 26Q98K0076 as an example of a control sample ID. The reviewer identified that this does not match the standard naming format used in production. Changed to 25357Q0020.

--exclude help text

The --exclude argparse help string did not mention the default '*Q*' exclusion, making it easy to assume the flag controlled all exclusions. The help text now explicitly states that the default control-sample exclusion is separate and is managed via --no-exclude-controls.

Retrospective analysis plan — completed status

retrospective/RETROSPECTIVE_ANALYSIS_PLAN.md describes the analysis plan in present tense, which reads as if the work is still pending. A status notice was added at the top: “Analysis complete (May 2026). This document records the plan that was followed. Results are in known_contaminated_samples.tsv and run_manifest.tsv.”

06 Design decisions confirmed by review

Several review comments questioned choices that turned out to be intentional and well-reasoned. These are documented here so the rationale is not lost.

✓
_MAX_GNOMAD_AF as a named constant
Not moved inline into argparse

The 0.40 threshold is empirically derived — validated against 15 false-positive markers all with gnomAD AF >0.40 and 17/18 genuine contamination markers with AF <0.40. A named constant at the module level carries this comment; an inline default in argparse would be a poorly documented magic number.

Intentional
✓
_LOG2_RANGE not in argparse
±4 log2 range stays internal

_BIN_WIDTH is already exposed as --bin-width. _LOG2_RANGE = 4.0 is a pure internal algorithm constant — ±4 log2 comfortably spans any plausible contamination fraction. Exposing it as a CLI flag would add interface noise for a parameter users should never change (and reducing it could silently miss real signals).

Intentional
✓
_DEFAULT_EXCLUDE as a named constant
Not moved inline into argparse

Same rationale as _MAX_GNOMAD_AF. The ['*Q*'] exclusion is an always-on default controlled by a disable flag (--no-exclude-controls), not an append flag (--exclude). This different pattern is clearer with a named constant.

Intentional
~
contamination_fraction precision
Bin-centre estimation is a known limitation

At bin_width=0.2, discrete bin centres near log2=−1 give fractions 0.44, 0.50, 0.57. This is inherent to the histogram approach. The tool is designed for detection, not precise quantification. Documented in the README. A curve-fit on in-peak variants would give better precision but is a future enhancement.
