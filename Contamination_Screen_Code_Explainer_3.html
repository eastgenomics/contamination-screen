01 Log2 ratios — why log2, not plain ratios?

The core of the algorithm computes VAF_B / VAF_A for every shared variant. The raw ratio has an asymmetry problem: a ratio of 2.0 (B has twice A's VAF) is just as "far from 1" as a ratio of 0.5 (A has twice B's VAF), but on a linear scale they look different — one is +1 unit from 1, the other is −0.5 units from 1.

Taking the log₂ fixes this symmetry:

log₂(2.0) = +1.0
log₂(1.0) = 0.0 ← no contamination
log₂(0.5) = −1.0

Now both directions are symmetric around zero. A positive log2 ratio means B has the higher VAF (B is the source); a negative log2 ratio means A has the higher VAF (A is the source). The magnitude tells you the contamination fraction, and the sign tells you the direction.

How to read a log2 ratio value

log2(ratio)Actual ratio (VAF_B / VAF_A)Interpretation
0.01.0Both samples have identical VAF — shared germline or swap
−1.00.5VAF_B is half VAF_A — ~50% contamination, A is source
−2.00.25VAF_B is a quarter VAF_A — ~25% contamination, A is source
+1.02.0VAF_B is double VAF_A — ~50% contamination, B is source
−3.00.125~12.5% contamination, A is source
In the code

np.log2(ratios.values) in _compare() computes log2 of every ratio at once using numpy's vectorised operation. This is orders of magnitude faster than calling math.log2() in a Python loop over each row.

Why not log10 or natural log?

Log₂ is used because the contamination signal typically produces peaks at multiples of 1 on the log₂ scale (−1 for ~50%, −2 for ~25%, etc.), making results visually interpretable. Any logarithm base would work for the algorithm — log₂ is a readability choice.

02 Histograms in numpy

A histogram counts how many values fall into each of a set of fixed-width bins. In this tool, the bins cover log2 ratios from −4 to +4, each 0.2 units wide. The histogram turns a list of ~20–100 ratio values into a shape — a curve with peaks and troughs.

How np.histogram() works

# Example: a contaminated pair with 5 shared variants
log2_ratios = [-1.05, -0.98, -1.02, -1.10, 0.03]

# np.histogram returns (counts_array, bin_edges_array)
counts, edges = np.histogram(log2_ratios, bins=[-1.2, -1.0, -0.8, -0.2, 0.2])

# counts = [1, 3, 0, 1]  — 1 value in [-1.2,-1.0), 3 in [-1.0,-0.8), etc.
# edges  = [-1.2, -1.0, -0.8, -0.2, 0.2]  — the bin boundaries

# Bin centres = (edges[:-1] + edges[1:]) / 2
centers = (edges[:-1] + edges[1:]) / 2
# centers = [-1.1, -0.9, -0.5, 0.0]

# The bin with the most values is the peak
idx_peak = np.argmax(counts)   # idx_peak = 1  (the -1.0 to -0.8 bin)
peak_center = centers[idx_peak] # peak_center = -0.9
  • 1
    np.histogram(values, bins=edges) returns two arrays: counts (how many values fell in each bin) and edges (the bin boundaries, always one element longer than counts). For N bins you need N+1 edge values.
  • 2
    Bin centres are computed as (edges[:-1] + edges[1:]) / 2. edges[:-1] is all edges except the last; edges[1:] is all edges except the first. Averaging them pairwise gives the midpoint of each bin.
  • 3
    np.argmax(counts) returns the index of the maximum value in the counts array. Using that index on centers gives the log2 position of the tallest bin — the peak.

How the code generates the bin edges

edges = np.arange(
    -_LOG2_RANGE - bin_width / 2,   # start: -4.1 (half-bin before -4.0)
     _LOG2_RANGE + bin_width,         # stop:  +4.2 (ensures +4.0 is included)
     bin_width,                       # step:  0.2
)

The start is shifted back by half a bin width so that a ratio of exactly 1.0 (log2 = 0.0) falls in the centre of a bin, not on a bin edge. This prevents a clean signal being split between two adjacent bins.

03 Z-scores — what they are and why they're used here

A z-score expresses a value as the number of standard deviations it is above or below the mean of a group. It answers the question: "Is this value unusual compared to the others?"

z = (value − mean) / standard_deviation

In this tool, the value is n_shared — how many variants two samples share. The mean and standard deviation are computed across all pairs in the run. A z-score of 2.0 means the pair shares variants at a rate that is 2 standard deviations above average for this run, which is unusual.

Why is it computed within a single run?

Two VEP configurations have been used in the Uranus pipeline at different times. The newer config (gnomADg + gnomADe) produces a mean n_shared ≈ 19 per pair; the older config (gnomADe only) produces a mean ≈ 8. These are different populations. If you pooled all 100 runs and computed a global z-score, a pair from an older run with n_shared = 14 would look wildly elevated (7+ SDs above the older config mean of 8), when in fact it is normal for that config.

By computing z-scores within each run, the baseline adapts automatically. A pair with n_shared = 14 on an older-config run has a z-score determined by the distribution of that run alone.

In the code

n_mean = df["n_shared"].mean()
n_std  = df["n_shared"].std()
df["n_shared_z"] = (df["n_shared"] - n_mean) / n_std if n_std > 0 else 0.0

The if n_std > 0 else 0.0 guard handles the edge case where all pairs have identical n_shared (zero variance) — dividing by zero would produce NaN values. In that edge case all z-scores are set to 0.0, and no pair would be flagged on the z-score criterion alone.

What z = 2.0 means in practice

For a normally distributed variable, about 97.7% of values fall below a z-score of 2.0. So a pair with n_shared_z ≥ 2.0 is in the top ~2.3% of pairs by shared variant count for that run. Combined with peak_count ≥ 10, this dual threshold means a pair must be unusual in two independent ways before it is flagged.

04 NaN — Not a Number

float("nan") is a special floating-point value meaning "no result". It is used extensively in the results dicts to fill in columns that could not be computed — for example, if a pair has fewer than 2 shared variants, there is no histogram to analyse, so all peak-related columns are set to NaN.

Key NaN behaviours to know

05 pandas DataFrame merges

The heart of _compare() is a DataFrame merge — finding variants that exist in both samples. This is equivalent to a SQL inner join on the variant coordinates.

# df_a has variants for sample A; df_b has variants for sample B
# We want rows where both samples have the same chr:pos:ref:alt

merged = pd.merge(
    df_a[["chrom", "pos", "ref", "alt", "af", "gene"]].rename(
        columns={"af": "af_a"}),       # ①
    df_b[["chrom", "pos", "ref", "alt", "af"]].rename(
        columns={"af": "af_b"}),       # ②
    on=["chrom", "pos", "ref", "alt"], # ③
    how="inner",                       # ④
)
  • ①
    Select and rename columns from sample A. Only the columns needed for comparison are selected. The af column is renamed to af_a so that after the merge we can tell which allele frequency came from which sample. The gene column is kept for detail TSV output.
  • ②
    Select and rename columns from sample B. Same pattern — af becomes af_b.
  • ③
    The join key: on=["chrom","pos","ref","alt"]. A variant is only considered "shared" if all four coordinates match exactly. Two variants at the same position but with different alt alleles (e.g. a C→T and a C→G at the same base) are not shared. This is why normalisation (bcftools norm -m -any) must have been run first — without it, the same variant might appear with different representations.
  • ④
    how="inner" means only rows present in both DataFrames are kept. Variants unique to one sample are dropped. This is the correct behaviour — we only want variants that can be meaningfully compared.

After the merge, each row of merged represents one variant seen in both samples. The ratio is then computed as a new column:

merged["ratio"]      = merged["af_b"] / merged["af_a"]
merged["log2_ratio"] = np.log2(merged["ratio"].values)

06 Calling external programs with subprocess

Python's subprocess module lets you run external programs and capture their output. Two patterns are used in this code:

Pattern 1 — subprocess.run() for simple commands

Used in _run() and wherever a single bcftools command is needed (e.g. indexing).

result = subprocess.run(
    ["bcftools", "view", "-h", str(vcf)],  # ①
    stdout=subprocess.PIPE,                 # ②
    stderr=subprocess.PIPE,                 # ③
    check=False,                            # ④
)
output_text = result.stdout.decode()        # ⑤
exit_code   = result.returncode             # ⑥
  • ①
    Command as a list of strings. Each word is a separate list element — never use a single string like "bcftools view -h file.vcf", as that requires shell=True which is a security risk. The list form is safe and explicit.
  • ②
    stdout=subprocess.PIPE tells Python to capture the program's standard output (what would normally print to the terminal) and make it available as result.stdout (a bytes object).
  • ③
    stderr=subprocess.PIPE captures error messages. If you don't capture stderr it goes straight to the terminal, which can be confusing. Capturing it lets the code decide whether to log it or raise an error.
  • ④
    check=False means Python will not raise an exception if the command exits with a non-zero return code. The code checks result.returncode manually. check=True (used in the _run() wrapper) raises subprocess.CalledProcessError automatically.
  • ⑤
    .decode() converts bytes to a Python string. All subprocess output comes back as bytes. .decode() uses UTF-8 by default, which is correct for bcftools output.
  • ⑥
    returncode. 0 means success; any non-zero value means the command failed. bcftools uses 1 for errors.

Pattern 2 — subprocess.Popen() for piped commands

Used in filter_vcf() to chain four bcftools commands together, just as you would with | in the shell.

# Shell equivalent:
# bcftools view -f PASS input.vcf.gz | bcftools filter -e ... | bcftools +split-vep ... | bcftools view -Oz -o out.vcf.gz

p1 = subprocess.Popen(cmd1, stdout=subprocess.PIPE, stderr=subprocess.PIPE)
p2 = subprocess.Popen(cmd2, stdin=p1.stdout,        # ①
                      stdout=subprocess.PIPE, stderr=subprocess.PIPE)
p1.stdout.close()                                    # ②
p3 = subprocess.Popen(cmd3, stdin=p2.stdout,
                      stdout=subprocess.PIPE, stderr=subprocess.PIPE)
p2.stdout.close()
p4 = subprocess.Popen(cmd4, stdin=p3.stdout,
                      stdout=subprocess.PIPE, stderr=subprocess.PIPE)
p3.stdout.close()
  • ①
    stdin=p1.stdout connects p1's output directly to p2's input, creating a pipe. Data flows from p1 → p2 → p3 → p4 in memory, without any temporary files being written to disk. This is equivalent to the shell | operator.
  • ②
    p1.stdout.close() is called in the parent process after p2 has inherited the file descriptor. This is required so that when p2 finishes reading, p1 receives an end-of-file signal and can exit cleanly. If you don't close it, p1 may hang waiting for a reader that never finishes.

07 Deadlock prevention — why _drain_stderr() exists

This is one of the subtler parts of the code. It exists to prevent a specific failure mode that is easy to trigger but hard to diagnose.

What is a pipe buffer?

When one process writes to a pipe and another process reads from it, the OS maintains a small buffer (typically 64KB on Linux). If the writing process fills this buffer before the reading process has consumed it, the writer blocks — it cannot write more until space is freed. If at the same time the reading process is waiting for the writer to finish before it starts reading, both processes wait for each other forever. This is a deadlock.

The problem in filter_vcf()

Processes p1, p2, and p3 all write error messages to their stderr pipes. The parent process (Python) only reads p4's output directly. If p1, p2, or p3 write more than 64KB to stderr (which can happen with large VCFs or certain bcftools warnings), their stderr buffer fills up, they block, and the entire pipeline stalls.

The fix: background drain threads

def _drain_stderr(stream, collector: list) -> None:
    """Read all stderr from a subprocess pipe into collector list."""
    collector.append(stream.read())  # blocks until EOF, then stores bytes

# In filter_vcf(), for each of p1, p2, p3:
stderr_collectors = {p: [] for p in (p1, p2, p3)}
drain_threads = [
    threading.Thread(target=_drain_stderr, args=(p.stderr, stderr_collectors[p]))
    for p in (p1, p2, p3)
]
for t in drain_threads:
    t.start()     # each thread immediately starts reading stderr

_, p4_err = p4.communicate()   # main thread waits for p4 to finish
for t in drain_threads:
    t.join()      # then wait for drain threads to finish

Each drain thread continuously reads from one process's stderr pipe. Because the reads happen in a background thread, the subprocess never blocks — it can always write more stderr. The collected bytes are stored in stderr_collectors and only examined later when checking return codes.

Why not just use communicate()?

subprocess.communicate() safely handles deadlocks for a single process, but you cannot call it on p1, p2, p3 sequentially — you would first have to finish p1 before starting p2, which defeats the purpose of piping. The background drain thread pattern is the standard solution for multi-stage pipelines.

08 ThreadPoolExecutor — parallel pairwise comparisons

Phase 3 must run hundreds or thousands of pairwise comparisons. Running them one at a time on a single CPU would be slow. The code uses a ThreadPoolExecutor to run many comparisons simultaneously.

# Build the task list — one tuple per pair
tasks = [
    (na, nb, df_cache, args.bin_width)
    for na, nb in combinations(sample_names, 2)  # ①
]

# Run all tasks in parallel, collect results in order
with ThreadPoolExecutor(max_workers=args.threads) as executor:
    raw_results = list(executor.map(_worker, tasks))  # ②
  • ①
    combinations(sample_names, 2) generates all unique pairs. For 30 samples this is 435 tuples. Each tuple is packed with the sample names, the shared DataFrame cache, and the bin width setting — everything _worker() needs.
  • ②
    executor.map(_worker, tasks) is like Python's built-in map() but runs the function calls in parallel across the thread pool. It returns results in the same order as the input tasks, and wraps everything up when all tasks are done. The with block ensures threads are properly shut down even if an exception occurs.

Why threads and not processes?

Python has a Global Interpreter Lock (GIL) that prevents true parallel CPU execution across threads for pure Python code. However, numpy and pandas operations release the GIL — they run compiled C code underneath. Because _compare() spends most of its time in pd.merge() and np.histogram(), threads do provide genuine parallelism here, without the significant overhead of spawning separate processes (which would require serialising and deserialising the entire df_cache for each process).

Thread safety in this code

df_cache is read-only during Phase 3 — no thread ever modifies it. Each thread creates its own local variables and returns a plain dict. Plain Python dicts are thread-safe to collect into a list via executor.map(). If any thread modified shared state, the code would need locks — but it is carefully designed to avoid that.

09 Path objects from pathlib

Every file path in the code is a Path object. If you have only seen string-based path manipulation before ("results/" + filename), here is what to know:

from pathlib import Path

outdir = Path("results")

# Join paths with /  (works on Windows and Linux)
filtered_dir = outdir / "filtered"   # Path("results/filtered")
dst = filtered_dir / vcf.name         # Path("results/filtered/sample.vcf.gz")

# File metadata
vcf.name    # "sample_annotated.vcf.gz"  — filename only
vcf.stem    # "sample_annotated.vcf"     — no final extension
vcf.suffix  # ".gz"                      — final extension

# Check existence and create directories
if dst.exists():
    ...
outdir.mkdir(parents=True, exist_ok=True)  # creates results/ if needed

# Convert to string when bcftools needs it
subprocess.run(["bcftools", "view", str(dst)])
Why str(path) when calling bcftools?

subprocess expects strings in the command list, not Path objects. str(path) converts cleanly. Most bcftools calls in the code wrap Path objects in str() for exactly this reason.
