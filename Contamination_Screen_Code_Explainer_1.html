01 What is this file?

contamination_screen.py is a self-contained command-line Python script. You run it once per sequencing run. It takes a folder of annotated VCF files — one per patient sample — and checks every possible pair of samples for cross-sample DNA contamination.

The core idea is simple: if a small amount of DNA from Patient A ended up in Patient B's library by mistake, then A's variants will show up in B's VCF at a consistently diluted allele frequency. The tool detects this by computing the ratio of allele frequencies between every pair of samples and looking for a statistical cluster at a non-unity ratio.

Before you read the code

Read Contamination_Screen_Code_Review_Briefing.html first. It explains the algorithm visually — what a log2-ratio histogram is, why we use it, and what the peaks mean. Understanding the what and why makes the how (the code) much easier to follow.

What it is not

This tool does not call variants, align reads, or assess quality. It works entirely on pre-processed VCFs from the end of the Uranus clinical pipeline. It expects VCFs that have already been variant-called, soft-filtered, normalised with bcftools norm -m -any, and annotated by VEP. Think of it as a QC layer on top of an existing pipeline, not a replacement for any part of it.

03 The four phases

The main() function at the bottom of the file runs four phases in sequence. Every other function in the file exists to serve one of these phases. If you understand what each phase does, the rest of the code falls into place.

Phase 1
Pre-filter VCFs
filter_vcf()
Phase 2
Load into memory
load_vcf()
Phase 3
Pairwise comparison
_compare() · _find_peaks()
Phase 4
Flag and write outputs
_apply_flags() · write_*()

Phase 1 — Pre-filter VCFs

Each input VCF is run through a four-stage bcftools pipeline that strips out low-quality variants and one specific population-frequency artefact. The output is a smaller, filtered VCF written to a filtered/ subdirectory. These filtered VCFs are cached on disk — if you re-run the tool with the same settings, Phase 1 is skipped for any VCF already filtered.

Why filter at all? The pairwise comparison in Phase 3 computes VAF ratios. If a variant has very low read depth, its VAF is noisy and the ratio is meaningless. Filtering ensures every variant that reaches Phase 3 has a reliably measured allele frequency.

Phase 2 — Load into memory

Each filtered VCF is queried with bcftools query to extract just the columns needed for comparison: chromosome, position, ref, alt, filter status, allele frequency, and gene name. These are loaded into pandas DataFrames — one per sample — and stored in a dictionary called df_cache. The rest of the file never touches VCF files directly; it only works with these DataFrames.

Phase 3 — Pairwise comparison (the core algorithm)

This is the most computationally intensive phase. For N samples, there are N×(N−1)/2 unique pairs. For a 30-sample run that is 435 pairs; for 96 samples it is 4,560. Each pair is processed by _compare(), which merges the two DataFrames on shared variant positions, computes log2(VAF_B / VAF_A) for each shared variant, and finds peaks in the resulting histogram using _find_peaks().

Phase 3 uses a ThreadPoolExecutor to run comparisons in parallel across multiple CPU threads. The per-pair results are plain Python dictionaries that are collected into a list.

Phase 4 — Flag and write outputs

The list of raw comparison results is converted to a pandas DataFrame by _apply_flags(), which computes within-run z-scores and applies all three flagging thresholds. Output functions then write summary.tsv, matrix.tsv, per-pair detail TSVs, and optionally histogram plots for the top flagged pairs.

The key insight

Phases 1 and 2 are preparation. Phase 4 is reporting. Phase 3 is where the science happens. When reviewing the code, spend most of your time understanding _compare() and _find_peaks().

04 Data flow

The most important thing to understand about the code structure is what form the data takes at each stage. The same variant information is represented four different ways as it moves through the pipeline:

StageData formWhere storedKey variable
Raw input VCF file on disk (.vcf.gz + .tbi) Disk — original VCF directory vcf_files (list of Paths)
After Phase 1 Filtered VCF file on disk Disk — results/filtered/ filtered_vcfs (dict: name → Path)
After Phase 2 pandas DataFrame — one row per variant RAM df_cache (dict: name → DataFrame)
During Phase 3 Merged DataFrame of shared variants + log2 ratios RAM (temporary, per pair) merged (inside _compare())
After Phase 3 List of plain Python dicts — one per pair RAM raw_results
After Phase 4 pandas DataFrame — one row per pair, with flags RAM + written to summary.tsv summary_df
Why not keep everything as DataFrames?

Phase 3 runs in parallel threads. Python's pandas DataFrames cannot be safely modified by multiple threads at the same time. Each thread is given read-only access to df_cache and returns a simple Python dict — which is thread-safe to collect into a list. The list is converted to a DataFrame only once, in Phase 4, in the main thread.

The sample name as the key

Throughout the code, samples are identified by their sample name — the column header from the VCF #CHROM line (the last field). This name is extracted once by get_sample_name() and used as the dictionary key in df_cache and filtered_vcfs, and as the value in sample_names (a list used to preserve order). Whenever you see name_a or name_b in the code, it refers to this sample name string.

The +split-vep plugin is required — it is bundled with bcftools 1.14+. If you see an error like "split-vep: command not found", your bcftools installation is either too old or was compiled without plugins. Check with bcftools --version and bcftools plugin --list.

How the functions call each other

The call graph is shallow — most functions are called only by main() or by one other function. Here are the only multi-level chains:

CallerCallsNotes
main() filter_vcf() Once per VCF in a loop
filter_vcf() _csq_gnomad_fields(), _drain_stderr(), _run() Helpers for the bcftools pipeline
main() _worker() via ThreadPoolExecutor Once per pair, in parallel
_worker() _compare() Thin unpacking wrapper
_compare() _find_peaks() Called once per pair with the log2 ratio array
main() _compare() again (directly) Second call for flagged pairs only, this time with include_shared_df=True to get the per-variant DataFrame for detail output
Why is _compare() called twice?

Phase 3 runs all pairs in parallel with threads and discards the per-variant DataFrames to save memory. Only after flagging are the top flagged pairs re-run with include_shared_df=True to retrieve the variant-level detail needed for TSVs and plots. Doing it this way avoids holding ~N²/2 DataFrames in RAM for an entire run.

Functions you can ignore on first reading

If you are new to the codebase, these functions are straightforward and do not need deep study:

  • _run() — just subprocess.run() with one extra log line
  • write_summary() — literally one line: df.to_csv()
  • write_matrix() — fills a numpy matrix and writes it as a DataFrame
  • _load_freemix() — reads a TSV and returns a dict
  • _worker() — four lines including the docstring
  • write_plots() — matplotlib boilerplate; only relevant if you care about plot output

Functions that deserve careful study

  • filter_vcf() — piped subprocesses with deadlock prevention; the bcftools pipeline design
  • _find_peaks() — the numpy histogram logic; understanding "overall" vs "non-unity" peak
  • _compare() — the core algorithm; DataFrame merge, ratio calculation, directionality
  • _apply_flags() — the z-score calculation and compound flagging condition
  • main() — the Phase 1 cache invalidation logic; how ThreadPoolExecutor is set up
